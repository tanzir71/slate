# Performance reference

The release reference is GitHub Actions' Linux runner, with Node 24, the lockfile and Playwright 1.65.1. CI enforces **p95 < 16 ms** on the real 50,000-word sheet in Chromium, Firefox, WebKit and mobile Chromium. Pages publication repeats Chromium/Firefox/WebKit on Linux. No profile is retried to select a passing timing and no threshold is increased. A failed reference run blocks the candidate.

The handover specifies the budget and browser tooling without specifying hardware. Choosing one declared reference is the implementation assumption for that missing detail. Windows/macOS still require their types, lint, unit/Rust tests, native builds and supported-browser functional tests. Their typing benchmarks run as diagnostics and retain reports when over budget. These measurements remain failures in the reports; they do not establish compliance on those hosts.

This follows observed host-dependent frame timing rather than a large-document-only slowdown. In CI 44181834323, macOS Chromium measured 88.5 ms on 50k words versus 110.1 ms on the short-note control; WebKit measured 40 ms versus 47 ms; mobile Chromium measured 100.4 ms versus 112.7 ms. Linux CI 44178565874 passed all profiles at 5.8/8/15/12.5 ms. CI 44190380062 also passed the complete Linux reference. Clock precision/frame scheduling and shared-runner load affect the measurement; the comparison does not prove their exact cause. Reports include both controls, frame timestamps, focus/visibility and recovery/handler costs. Improve the app or investigate the environment when the reference fails; never substitute the short-note result for the required measurement.

Run `pnpm perf:typing` after `pnpm build:site`, with other builds and browser suites stopped. It is a separate Playwright process with isolated report directories. Each document receives 225 real inputs; both the short control and the 50k-word source file are checked byte-for-byte after typing. The 50k-word file is also checked before measuring. Setup imports and opens that real Markdown file through the public UI rather than injecting all 50k words into contenteditable in one operation. Bulk insertion/paste is a separate workload: the Docker WebKit trace spent 30 seconds in that setup operation and expired before collecting all typing samples. Recovery remains enabled. The final assertion remains `< 16`, including on diagnostic hosts when invoked locally, and the whole-test timeout remains 60 seconds. `pnpm verify` retains its strict local checks; CI's documented platform workaround separates required functional verification from these host diagnostics. Windows WebKit OPFS checks use the existing Linux/macOS capability workaround.

Lighthouse uses the same Linux reference for its unchanged score/LCP/CLS budgets; macOS remains a diagnostic because its parser/layout timing differs. Pixel comparisons use a separate digest-pinned Linux Chromium container, described in [visual testing](visual-testing.md). No timing data from that container replaces the typing reference.

Typing uses the normal product configuration: live preview and synchronous recovery remain active. Derived sheet metadata refreshes in bounded 100 ms windows throughout input, using the latest immutable snapshot; file saves follow their existing path. The benchmark waits for the final 50,045-word HUD as well as checking the saved Markdown, so summary work must catch up before the case can pass. This refresh policy applies to the app itself and is covered by worker-request and continuous-update regressions.
